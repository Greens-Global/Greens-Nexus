## What changed on Sep 22

Microsoft retired the legacy Actionable Messages token on June 8, 2026.
Clicks are now authenticated with a Microsoft Entra ID token issued by our
tenant to Microsoft's Actions app. `routers/mail_actions.py` validates that token
(Sagar's ddc00e13 plus both issuer spellings and both audiences). The card is
emitted only when BOTH `NEXUS_AM_ORIGINATOR` and `NEXUS_AM_AUDIENCE` are set,
so a half-done registration never ships a card whose buttons all fail.

Reference: https://learn.microsoft.com/outlook/actionable-messages/enable-entra-token-for-actionable-messages

## Steps (in order)

1. **Entra app registration** (Azure Portal > Microsoft Entra ID > App
   registrations > New registration). Name "Greens Nexus Mail Actions",
   "Accounts in this organizational directory only", no redirect URI.
   Copy the Application (client) ID.
2. **Provider registration** at https://outlook.office.com/connectors/oam/publish
   (sign in as the person who will own it; Test Users scope needs no admin).
   - Friendly name: Greens Nexus
   - Sender email address: the value of `NEXUS_FROM_EMAIL` on the App Service
     (Configuration > Application settings). The inbound task mailbox is
     nexus@greensglobal.com; confirm the sender is the same mailbox before
     submitting, the card only renders when From: matches exactly.
   - Target URLs (both, one registration serves dev and prod):
     - https://greens-nexus-api-dev-a6fad4brawevg8de.westus2-01.azurewebsites.net
     - https://greens-nexus-api-ejfxdjcbevfxb2ht.westus2-01.azurewebsites.net
   - Scope: **Test Users** first (auto-approves; list the testers, e.g.
     visesh.lodha@greensglobal.com; pranshu.pandey@greensglobal.com). Submit a
     second registration with scope **Organization** once the card is proven;
     that one routes to an Exchange/Global admin for approval.
   - MsEntra Auth: Application ID = the client ID from step 1. The form
     generates an **AppIdUri** (`api://auth-am-<guid>/<guid>`); copy it.
   - Save. The dashboard shows the **Provider ID** (originator GUID).
3. **Expose the API** (back on the app registration > Expose an API):
   - Application ID URI = the AppIdUri from step 2, exactly.
   - Add a scope, e.g. `Actions.Invoke`, "Admins only" can consent, any
     display text. (Done 09/23 via the CLI: scope `Actions.Invoke`.)
   - Add a client application: `48af08dc-f6d2-435f-b2a7-069abd99c086`
     (Microsoft's Actions app), tick the scope. This pre-authorizes it, so no
     consent prompt is ever shown.
4. **App Service settings** on `greens-nexus-api-dev` and `greens-nexus-api`
   (prod: mark each as a Deployment slot setting, otherwise the next slot swap
   wipes it - see the Aug 5 note in memory):
   - `NEXUS_AM_ORIGINATOR` = Provider ID
   - `NEXUS_AM_AUDIENCE` = `<AppIdUri>,<Application (client) ID>` - the v1
     token's audience, then the v2 token's, comma-separated; both accepted.
   Restart. No code deploy needed beyond the Sep 22 change.
5. **Verify** (registration takes up to 24 h to activate):
   - `GET /health` shows `"actionable_messages": true`.
   - Task email settings (My Tasks > Email Settings, admin config) must have
     the event enabled; on dev every task event is currently OFF.
   - Assign a task to a test user, open the email in Outlook (web is the
     quickest), click Mark Complete: the card should refresh to "Marked
     complete by you." and the task closes in Nexus.
   - A click that fails shows the reason under the card
     (`CARD-ACTION-STATUS`): "not configured" = step 4 missing on that
     environment; "another tenant" / "Invalid" = step 3 audience does not
     match `NEXUS_AM_AUDIENCE`.
